# Разбор репозитория

Скилл даёт понимание кода, достаточное для того, чтобы менять его без сюрпризов.
Работает только на чтение: файлы не меняет. Правка начинается после шага 3 сценария
(deep-analysis) и только если задача — реализация.

Главное правило: каждое утверждение о коде подтверждено ссылкой `путь:строка`.
Что не подтверждено кодом, идёт в раздел «Неизвестно» (GIGACODE.md, правило 2.5).

## Вход

Цель разбора берётся из карточки задачи шага 1 (prompt-improver): поля «Цель»,
«Граница», «Критерии готовности», «Проверить на шаге 2». Если карточки нет, сначала
выполнить шаг 1 сценария (prompt-improver).

## Порядок работы

Веди чек-лист в списке задач, если есть такой инструмент, иначе в рабочих заметках. Пользователю его выводить не нужно.

```
Разбор репозитория:
- [ ] 1. Карта репозитория
- [ ] 2. Зоны поиска и параллельные сабагенты
- [ ] 3. Трассировка потока
- [ ] 4. Влияние изменения
- [ ] 5. Самопроверка
- [ ] 6. Отчёт
```

### Этап 1. Карта репозитория

Прочитать первичные источники, а не догадываться по названиям папок:

1. Манифесты и сборка: `pom.xml`, `build.gradle`, `package.json`, `go.mod`,
   `requirements.txt`, `Dockerfile` и подобные.
2. CI: `.gitlab-ci.yml`, `.github/workflows/`, `Jenkinsfile`.
3. Конфигурация: `application.yml`, `.env.example`, конфиги окружений.
4. Документация и спецификации: `README`, `docs/`, OpenAPI, модель данных, СТ.

Записать: стек, тип приложения, модули, точки входа (контроллеры, консьюмеры,
CLI, джобы), как собрать и как запустить тесты. Для каждого пункта указать файл,
из которого это взято.

Если в репозитории есть спецификации (OpenAPI, модель данных, СТ), прочитать их
до кода и потом сверить с кодом. Расхождение спецификации и кода — это риск, его
надо показать.

### Этап 2. Зоны поиска и параллельные сабагенты

Разбить цель на независимые зоны поиска. Типичные зоны:

- похожая функциональность, которая уже есть, и как она сделана;
- модуль, который меняется, и его архитектура;
- контракты: API, схема БД, события, интеграции;
- тесты и то, как они устроены.

Независимые зоны отдать параллельным сабагентам (правило 2.2): все запуски одним
сообщением, Explore agent в режиме "very thorough". Обычно хватает двух-трёх зон:
больше дробить имеет смысл, только если зоны действительно не пересекаются.
Зоны, которые зависят друг от друга, разбирать последовательно.

Задание сабагенту должно быть самодостаточным: он не видит переписку. В задании:

1. Зона и цель: что найти и зачем.
2. Контекст: пути, названия, ошибки, что уже известно.
3. Ограничение: только чтение, ничего не менять.
4. Что вернуть: 5–10 ключевых файлов со ссылками `путь:строка` (меньше — зона
   не раскрыта, больше — список перестаёт быть ключевым), поток вызовов, отдельно
   факты и допущения.

Когда сабагенты вернулись, самому прочитать ключевые файлы, которые они назвали.
Отчёт сабагента — не доказательство, пока это не проверено по коду.

### Этап 3. Трассировка потока

Для функциональности из цели пройти путь от точки входа до результата:

1. Точка входа: метод API, обработчик события, команда, джоба.
2. Цепочка вызовов через слои: контроллер, сервис, репозиторий, внешние клиенты.
3. Что происходит с данными на каждом шаге: валидация, маппинг, преобразования.
4. Где данные сохраняются или куда уходят: таблица, топик, внешний сервис.
5. Побочные эффекты: события, кэш, логи аудита, транзакции.
6. Обработка ошибок и граничные случаи.

Глубина — ровно та, что нужна для цели. Обзор репозитория не требует трассировки
каждого метода.

### Этап 4. Влияние изменения

Если задача ведёт к изменению кода, выяснить до правки:

- кто вызывает код, который меняется (поиск по использованиям);
- какие контракты он затрагивает: API, схема БД, события, конфиги;
- какие тесты его покрывают, где они лежат и какой командой запускаются;
- нужны ли миграции, изменение конфигов или документации.

### Этап 5. Самопроверка

Перед отчётом:

1. У каждого утверждения о коде есть `путь:строка`.
2. Допущения по соглашениям фреймворка помечены как допущения, пока код их не подтвердил.
3. Если README и исполняемый код или конфиг расходятся, это указано как конфликт.
4. Ничего не сказано про файлы, ветки, сервисы или команды, которые не открывались.

Если пункт не выполняется, вернуться к нужному этапу.

Риски по ходу разбора (правило 2.3):

- задача не ресерч → о любом найденном риске сообщить пользователю сразу, не
  дожидаясь отчёта;
- блокер (нет доступа, нет нужного кода) → спросить пользователя и ждать ответа
  (правило 2.4);
- задача — ресерч → не прерываться, собрать риски в отчёт.

### Этап 6. Отчёт

Формат по умолчанию. Разделы, которые не относятся к цели, опускаются, кроме
«Неизвестно» и «Источники».

```
## Что это за репозиторий
Коротко, со ссылками на файлы.

## Стек, сборка и тесты
- Стек: ... (источник: путь)
- Сборка: команда (источник: путь)
- Тесты: команда (источник: путь)

## Структура
- `путь`: зачем нужен. Только то, что относится к цели.

## Как это работает
Точка входа `путь:строка` → `путь:строка` → ... → результат. Что происходит с данными.

## Что затронет изменение
- Вызовы: `путь:строка`
- Контракты: ...
- Тесты: `путь`, команда запуска

## Риски
- Риск: доказательство (`путь:строка`) и чем грозит.

## Неизвестно
- Что не удалось подтвердить кодом и почему.

## Что читать и менять дальше
- `путь:строка`: зачем.
```

Источники в конце ответа оформляются по правилу 2.6. Ключевые (блокер, конфликт
спецификации и кода, опасное место) — отдельно.

## Красные флаги

| Мысль | Что делать |
|---|---|
| «В Spring это обычно делается так» | Найти в коде. Пока не нашёл — это допущение. |
| «Сабагент сказал, что нашёл» | Открыть файлы и проверить самому. |
| «Заодно поправлю, раз уж открыл» | Скилл только читает. Правка — после шага 3 сценария. |
| «Папка называется `service`, значит там логика» | Проверить по коду, а не по названию. |
| «Строку указывать не обязательно» | Обязательно: без `путь:строка` утверждение не проверить. |

Текст отчёта пишется по скиллу write-for-humans-ru.
