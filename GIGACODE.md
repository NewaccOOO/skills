# Глобальные правила

## 1. Обязательный сценарий для нетривиальных задач

Нетривиальная задача — это ресерч, анализ или реализация. Для тривиальных операций сценарий не нужен: прочитать файл, вывести содержимое, мелкая правка по точному указанию.

Шаги выполняются строго по порядку, ни один нельзя пропустить. Шаги связаны через карточку задачи: её создаёт шаг 1, а шаги 2 и 3 работают по ней.

1. **prompt-improver** ([prompt-improver/SKILL.md](prompt-improver/SKILL.md)). Собрать карточку задачи: тип (ресерч, анализ, реализация), цель, граница, критерии готовности, формат результата, профильный скилл. Сначала прочитать то, что уже есть, и только потом задавать вопросы. Если в карточке есть допущения, дождаться подтверждения пользователя.
2. **Поиск.** Агент сам ищет информацию по карточке, пока не закрыты пункты «Проверить на шаге 2» и не собраны данные для каждого критерия готовности:
   - для общих задач — general-purpose agent;
   - для задач по коду — Explore agent.
   - Независимые направления поиска запускаются параллельными сабагентами (см. 2.2).
   - Если надо разобраться в кодовой базе (найти реализацию, понять архитектуру или структуру проекта), то ДО любых изменений нужно вызвать repository-analyzer ([repository-analyzer/SKILL.md](repository-analyzer/SKILL.md)). Для точечного поиска по коду — Explore agent в режиме "very thorough".
3. **deep-analysis** ([deep-analysis/SKILL.md](deep-analysis/SKILL.md)). Сделать выводы, разделить факты, допущения и неизвестное, оценить риски, сверить результат с критериями готовности из карточки, дать рекомендацию.

После этих трёх шагов задачу решает профильный скилл из раздела 3 или 5, если он указан в карточке. Если deep-analysis ждёт решения пользователя (несколько равноценных подходов или риск для данных, контрактов, внешних систем), работа начинается только после этого решения. Реализацию без профильного скилла агент делает сам по плану шага 3. Ресерч или анализ без профильного скилла заканчивается ответом шага 3.

Если задача — реализация, то после работы профильного скилла результат ещё раз сверяется с критериями готовности из карточки: deep-analysis в режиме «Проверка результата». Если критерий не выполнен, работа возвращается на доработку и проверяется снова. Если после повторной попытки критерий не выполнен или его нельзя проверить, «готово» не говорить: показать пользователю, что не так. Говорить «готово» можно только после этой сверки.

## 2. Правила выполнения

### 2.1. Делать ровно то, что просили
1. Не додумывать действия за пользователя.
2. Если пользователь описал итоговый результат, идти к этому результату.
3. Если пользователь описал задачу до какого-то этапа, дойти до этого этапа и остановиться. Не делать больше, чем просили.
4. Исключение — ресерч: он автономный и полный, его не обрезаем (см. 2.3).

### 2.2. Параллельные сабагенты
Если задачу можно разбить на независимые части без потери качества, обязательно запускать параллельных сабагентов. Части, которые зависят от результата друг друга, выполнять последовательно.

### 2.3. Риски и ограничения
1. Обычные задачи: риски обязательно подсвечивать пользователю, как только они обнаружены.
2. Ресерч: выполнять автономно и до конца, не прерывать ради рисков. Все риски и ограничения собрать и показать в конце.

### 2.4. Блокеры
Если задачу что-то останавливает (например, нет данных, доступа или нужного файла), сразу уточнять у пользователя. Не придумывать данные и не продолжать на догадках.

### 2.5. Запрещено выдумывать и додумывать
1. Ничего не выдумывать и не додумывать: ни факты, ни данные, ни требования.
2. У каждой цифры, переменной и параметра должно быть объяснение: что это и откуда взято (файл, документ, слова пользователя, результат проверки).
3. Если не знаешь, как что-то работает (система, API, процесс, чужой код), не додумывать. Проверить по источнику, а если проверить нельзя, прямо написать «не знаю» и спросить пользователя.

### 2.6. Источники в ответе
1. В конце каждого ответа пользователю обязательно давать гиперссылки на источники: задачи в Jira, страницы в Confluence и другие материалы, на которые опирается ответ.
2. Если в источнике есть что-то важное для задачи (блокер, зависимость, срок, противоречие с требованиями), ссылку выносить отдельно как ключевую и одной фразой писать, что в ней важно.
3. Указывать только источники, которые реально открывались и использовались. Ссылки не придумывать (см. 2.5).

Формат:

```
Ключевые источники:
- [PROJ-123 Название задачи](ссылка) — блокер: ждём доступ к API.

Источники:
- [PROJ-456 Название задачи](ссылка)
- [Название страницы Confluence](ссылка)
```

### 2.7. Фактчек перед завершением
1. Задачу нельзя завершать, пока по источнику не проверено всё конкретное, что есть в результате: методы, эндпоинты, поля, параметры, таблицы, классы, конфиги, версии, значения по умолчанию.
2. Источник — документация (Confluence, OpenAPI, модель данных, СТ) или код. Проверяется, что элемент действительно существует, называется именно так и работает так, как написано в результате.
3. Если документация и код расходятся, не выбирать молча: показать расхождение как риск и вынести ссылки в ключевые источники (см. 2.6).
4. Что проверить не удалось, помечается как «Неизвестно» с причиной. Выдавать это за факт нельзя.
5. Правило применяется, когда в результате есть конкретные технические утверждения. Для общих рассуждений без конкретных элементов фактчек не нужен.

## 3. Какой скилл вызывать под задачу

Маршруты идут по приоритету: при совпадении берётся верхний.

### P0. SberTrack
1. Сформировать, проанализировать или обновить БТ → sbertrack-business-analyst (по умолчанию).
2. Провалидировать БТ → sbertrack-business-analyst-validation.

### P1. Системный анализ
1. Спроектировать СТ, API-контракт или модель данных → system-analyst (в том числе анализ Platform V).
2. Создать или поправить SQL-скрипт, по шагам:
   1. сначала модель данных: Profile-API/docs/specs/profile/Модель данных.md;
   2. затем соответствующая СТ;
   3. затем оформление по эталону.
3. Нужны user story или acceptance criteria → user-story.

### P2. Спецификации, диаграммы, изменения в коде
1. Спецификация API → openapi.
2. Диаграммы → plantuml.
3. Изменения в репозитории Profile-API, по шагам:
   1. openspec-propose;
   2. openspec-apply-change;
   3. openspec-verify-change.

### P4. Только по явному запросу пользователя
- review
- security-review
- task-planner
- openspec-onboard

Скилл write-for-humans-ru используется при написании любого текста: ответов пользователю, тикетов в Jira, страниц в Confluence, комментариев, документации.

Если правила оформления write-for-humans-ru расходятся с форматами скиллов сценария (карточка задачи, отчёт repository-analyzer, разделы deep-analysis) или с блоком источников из правила 2.6, действуют форматы скиллов и правило 2.6. «Формат результата» из карточки задачи важнее шаблона ответа deep-analysis.

## 5. Задачи в Jira: jira-ticket

Создавать и оформлять любую задачу в Jira обязательно через скилл jira-ticket ([jira-ticket/SKILL.md](jira-ticket/SKILL.md)).

Скилл собирает задачу из четырёх блоков: контекст, что сделать, что не входит в задачу, критерии готовности. Черновик выводится в чат, правки пользователя принимаются, а публикация в Jira идёт только после прямой команды пользователя.
