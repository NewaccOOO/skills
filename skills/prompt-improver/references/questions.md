## Плохие и хорошие вопросы

| Плохо | Почему | Хорошо |
|---|---|---|
| «Что именно нужно сделать?» | Вопрос без вариантов, перекладывает работу на пользователя | «Что править: 1) валидацию в `ProfileController.java:88` (рекомендую, там падает тест); 2) маппинг в `ProfileMapper.java:41`?» |
| «Какой подход использовать: A, B, C, D или E?» | Слишком много вариантов | Два-три варианта, рекомендуемый первым |
| «Нужны ли тесты и документация?» | Два решения в одном вопросе | Два отдельных вопроса |
| «Вы ведь хотите через REST?» | Наводящий вопрос | «Как отдавать данные: 1) REST, как остальные методы сервиса (рекомендую); 2) Kafka-событие?» |
| «Где лежит модель данных?» | Можно найти самому | Не спрашивать, найти на этапе 1 |

## Пример 1: размытый запрос

Запрос: «Разберись с полем канала связи в профиле».

Этап 1: в переписке есть ссылка на задачу Jira, в ней сказано, что уведомления уходят
только по SMS. В репозитории есть «Модель данных.md», поля канала в ней нет.

Вопросы:
1. Что нужно на выходе: 1) анализ, как добавить поле, без изменений (рекомендую:
   в задаче Jira нет согласованной СТ); 2) сразу реализация?
2. Какие значения канала поддерживаем: 1) `SMS`, `EMAIL`, `PUSH`, как в задаче Jira
   (рекомендую); 2) другой список?

Карточка после ответов «1» и «1»:

```
Карточка задачи

Тип: анализ
Цель: понять, что нужно изменить в Profile-API, чтобы хранить канал связи клиента.
Граница: только анализ и план изменений. Код, СТ и миграции не трогаем.
Критерии готовности:
1. Перечислены все места, которые меняются: модель данных, СТ, API, миграция, со ссылками на файлы.
2. Для каждого места указано, что именно меняется.
3. Названы риски для существующих данных.
Формат результата: ответ в чате.
Исходные данные: задача Jira [ссылка], «Модель данных.md».
Профильный скилл: system-analyst.
Проверить на шаге 2: есть ли уже похожее поле в соседних сущностях.
Допущения: нет.
```

## Пример 2: ясный запрос, вопросов нет

Запрос: «Найди все места, где Profile-API пишет в таблицу `client_contacts`, и дай
список со ссылками на строки».

```
Карточка задачи

Тип: ресерч
Цель: список всех мест записи в таблицу client_contacts.
Граница: только поиск, без изменений.
Критерии готовности:
1. Каждое место записи указано как файл:строка.
2. Для каждого места указан тип операции (INSERT, UPDATE, DELETE).
Формат результата: список в чате.
Исходные данные: репозиторий Profile-API.
Профильный скилл: нет.
Проверить на шаге 2: пишут ли в таблицу через ORM, а не только SQL.
Допущения: нет.
```

Допущений нет, поэтому сразу шаг 2 сценария.

## Пример 3: блокер

Запрос: «Сверь СТ с кодом сервиса уведомлений».

На этапе 1 выяснилось, что репозитория сервиса уведомлений в доступе нет. Это блокер
(правило 2.4): без кода сверку не сделать. Вопрос сразу:

«Репозитория сервиса уведомлений у меня нет. Как продолжить: 1) дайте доступ или
путь к репозиторию (рекомендую); 2) сверяю только СТ с OpenAPI-спецификацией, без кода?»
