# Шаблон правил

Темы правил одни и те же в обоих режимах. Отличается только раскладка: в режиме «Папка» —
отдельный файл `.mdc` на тему, в режиме «Все чаты» — один файл `user-rules.md` с разделом
на тему.

## Темы

| Тема | Файл в режиме «Папка» | О чём |
|---|---|---|
| Рабочий процесс | `workflow.mdc` | Этапы задачи по порядку и кто что делает на каждом, какие скиллы и команды где нужны, длинные автономные заходы или шаг за шагом, когда пользователь начинает новый чат и как переносит контекст, откуда приходят задачи. Чем агенту заниматься на каждом этапе |
| Постановка | `requests.mdc` | Что значат короткие реплики, что пользователь прикладывает, что подразумевает по умолчанию. Его словарь с расшифровкой |
| Поправки | `corrections.mdc` | Что пользователь исправлял больше одного раза и как делать сразу правильно |
| Ответы | `answers.mdc` | Язык, длина, формат, что показывать в чате, что значит «готово» и чем подтверждать результат |
| Автономность | `autonomy.mdc` | Что делать без спроса, что только по команде, когда спросить и как: все вопросы одним сообщением |
| Внешние системы | `tools.mdc` | Работа через MCP: по каждой системе — для чего она, как оформлять задачи, страницы и комментарии (поля, структура, заголовки, длина, тон), куда их класть и как называть, нужен ли черновик до записи и что можно писать без спроса |
| Проект | `project.mdc` | Только в режиме «Папка»: термины проекта, типичные задачи, что здесь проверять перед «готово» |

Тема без находок — ни файла, ни раздела.

## Лимиты

- В теме не больше 12 пунктов, пункт — одна-две строки.
- Правило должно оставаться верным через полгода: без путей к файлам, версий, хешей
  коммитов, номеров задач и дат.
- Без пометок силы, числа диалогов и ссылок на диалоги. Доказательства живут
  в `findings.jsonl` и в отчёте, а в правилах только то, что агенту делать.
- Правило уже есть — правь его формулировку или переставь выше, второе такое же не добавляй.

## Режим «Папка»

Правила лежат в `<корень>/.cursor/rules/collab/`. Cursor читает подпапки `.cursor/rules`,
но только файлы `.mdc` с frontmatter: обычный `.md` там игнорируется.

Каждый файл не длиннее 50 строк вместе с frontmatter. Не влезает — оставь то, что стоило
пользователю итераций, разовое убери.

```markdown
---
description: Как пользователь ставит задачи и что подразумевает
alwaysApply: true
---
```

`alwaysApply: true` — правило попадает в каждый чат этой папки. Так пиши все файлы, кроме
`tools.mdc`: ему ставь `alwaysApply: false` и описание вроде «Как заводить задачи и писать
страницы во внешних системах через MCP». Cursor подключает такое правило сам, когда агент
работает с этими системами, и не тратит на него контекст в остальных чатах. `globs`
не нужен: правила про человека, а не про файлы.

## Режим «Все чаты»

Один файл `~/.cursor/collab/user-rules.md` без frontmatter, не длиннее 150 строк. Это
исходник для User Rules: пользователь вставляет его текст в Customize → Rules → User Rules,
а при следующем запуске скилл дополняет этот же файл. Разделы — темы из таблицы выше,
заголовками второго уровня. Только правила про человека: термины и проверки конкретных
проектов сюда не идут.

## Как писать пункт

Пункт — правило в повелительном наклонении и, если без него непонятно, короткий пример
из диалогов. Пример — пересказ или цитата до 100 символов без имён коллег и без значений
секретов. Пример условный:

```markdown
# Поправки, которые уже были

- Сначала результат, потом подробности. Пример: «короче, что в итоге?».
- Не переспрашивай то, что есть в приложенном файле: прочитай его.
```

Рабочий процесс пиши нумерованным списком по порядку, у каждого этапа — что делает
пользователь и что агент. Пример условный, этапы бери из диалогов:

```markdown
# Как идёт работа

1. Задача приходит ссылкой на трекер задач или вставленной перепиской. Агент сам читает задачу
   и связанные страницы, не просит пересказать.
2. План пользователь смотрит до кода. Агент присылает план и ждёт ответа.
3. Код, тесты и проверку на стенде агент делает сам, без промежуточных вопросов.
4. Коммит и MR — только по команде пользователя.
```

Внешние системы пиши по одной системе на подраздел: для чего, формат записи, порядок
согласования. Пример условный:

```markdown
# Внешние системы

## Трекер задач
- Задачу заводи только после показа черновика в чате и ответа «да».
- Заголовок: «[компонент] что сделать», описание: суть, критерии приёмки, ссылки.
- Статус меняй сам, когда работа по задаче закончена и проверена.

## База знаний
- Новую страницу клади дочерней к той, что пользователь назвал. Не назвал — спроси.
- Страница начинается с того, зачем она нужна, без вступлений. Таблицы вместо длинных списков.
```

Не пиши в правилах:
- значения токенов, паролей, ключей и строк подключения;
- то, что уже есть в `AGENTS.md`, других правилах `.cursor/rules` или User Rules;
- разовые случаи без последствий;
- оценки пользователя вроде «нетерпеливый» или «придирчивый»: только то, что агенту делать.
